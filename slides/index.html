Code design skill


## Make illegal states unrepresentable

When modeling anything with a lifecycle or status (workflows, state machines, entity records), prefer types
that make invalid states impossible to construct over a single type with a mutable status field plus runtime
guards.

- Don't model state as one type with a `state`/`status` field alongside fields that only make sense in some
  states. This lets illegal combinations compile silently — e.g. a `CANCELLED` record still carrying a
  payload, or a terminal record getting passed to a function meant for active ones.
- Instead, give each state its own type (a discriminated union in TS, a sealed class/enum with associated
  data in Kotlin/Swift/Rust) carrying only the fields valid in that state. Write transition functions whose
  signatures only accept the state(s) they're legally callable from.
- Goal: an illegal call becomes a compile error, not a runtime check someone has to remember to write. If you
  catch yourself adding an `if (state !== X) throw` guard, that's usually a sign the type should have made
  the call impossible instead.

Example shape (TypeScript):
```ts
// Bad: state as a field, illegal calls still compile
interface Event { id: string; state: "STORED" | "APPLIED" | "CANCELLED"; payload: string }
function apply(e: Event): Event { ... } // accepts a CANCELLED event too

// Good: each state is its own type
interface Cancelled { tag: "CANCELLED"; id: string; reason: string }
interface Validated { tag: "VALIDATED"; id: string; payload: string }
function apply(e: Validated): Applied { ... } // no overload for Cancelled — won't compile
```

Apply this whenever you're about to add a runtime state check — ask first whether the type system can reject
the illegal call instead.

The property checklist

You don't need a model checker in hand to start thinking like one. For any design, ask: (1) what invariant must hold always? (2) what bad thing must never happen — a safety property? (3) what good thing must eventually happen — a liveness property? Answering these, in prose, before any code exists, is how you find the “sentence nobody wrote down” from Act 2, on paper, for free.

Transition: "And you can push that same discipline all the way down to a single function."

Design by Contract

The same thinking, pushed down to one function or interface: a precondition is what the caller owes you, a postcondition is what you owe the caller back, and the invariant holds across every call. No model checker required — just explicit discipline about what a boundary actually promises. The cheapest on-ramp into this mindset: write a contract on a function signature today.

Bertrand Meyer, “Applying 'Design by Contract'”, IEEE Computer, 1992

Formal method language - TLA+ example


Check(p) == \* step 1: record whether the guard looked okay
    /\ pState[p] = "check" \* only while p hasn't checked yet
    /\ checked' = [checked EXCEPT ![p] = (balance >= Amount)] \* verify the amount available
    /\ pState'      = [pState EXCEPT ![p] = "debit"] \* moves p to the debit step
    /\ UNCHANGED balance \* balance itself is untouched here

Debit(p) == \* step 2: act on what was recorded
    /\ pState[p] = "debit" \* only once p reached the debit step
    /\ balance' = IF checked[p] THEN balance - Amount ELSE balance \* apply the debit
    /\ pState'      = [pState EXCEPT ![p] = "done"] \* marks p finished
    /\ UNCHANGED checked \* checked stays as recorded in step 1

Next == \E p \in Procs : Check(p) \/ Debit(p) \* any process, either step, in ANY interleaving

NoOverdraft == balance >= 0 \* the invariant property to check balance >= 0
Line by line, click through: 1. Check(p) == — step 1, records whether the guard looked okay. 2. pState[p] = "check" — only enabled before p has checked. 3. checked' = ... balance >= Amount — remembers the READ, doesn't act on it yet. 4. pState' = ... "debit" — moves p to the debit step. 5. UNCHANGED balance — the balance itself isn't touched here, only recorded. 6. Debit(p) == — step 2, acts on what was recorded earlier. 7. pState[p] = "debit" — only once p reached the debit step. 8. balance' = IF checked[p] ... — THE BUG: debits based on the stale check from step 1, not a fresh read. This is exactly the check-then-act race. 9. pState' = ... "done" — marks p finished. 10. UNCHANGED checked — checked stays as recorded, not touched again. 11. Next == ... Check(p) \/ Debit(p) — any process can do either step, in any interleaving — that's what lets two processes both pass the check before either debits. 12. NoOverdraft == balance >= 0 — the property TLC finds a violation of.
